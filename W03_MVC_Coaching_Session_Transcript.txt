TRACY:
const getProjectDetails = async (projectId) => {
    const query = `
        SELECT p.*, o.name AS organization_name
        FROM project p
        JOIN organization o ON p.organization_id = o.organization_id
        WHERE p.project_id = $1
    `;
    const result = await db.query(query, [projectId]);
    return result.rows[0];
};

How the code works:

1. Accepting the Parameter: The function takes projectId as an argument. This is passed down from the controller, which extracts it from the URL (e.g., the 1 in /project/1).
2. The $1 Placeholder: In the SQL query, $1 acts as a placeholder. It tells PostgreSQL, "I am going to give you the value for this later."
3. The Parameter Array: In db.query(query, [projectId]), the second argument is an array. The database driver safely inserts projectId into the $1 slot.
4. The JOIN: The query joins the project table with the organization table so we can grab the organization's name (o.name AS organization_name) in the exact same request.
5. result.rows[0]: Because project_id is a primary key, this query will only ever return exactly one row (or zero rows if the ID doesn't exist). By returning result.rows[0], we pass back a single object instead of an array of objects.

Why I chose this approach:

1. Security (Preventing SQL Injection)
I used parameterized queries ($1 and the array) instead of concatenating strings (like `WHERE project_id = ${projectId}`). If a user typed something malicious into the URL, string concatenation would allow them to execute raw SQL (SQL Injection). By passing it as a parameter array, the pg library escapes the input, making it impossible to hack the database this way.

2. Avoiding Multiple Database Calls (Performance)
I used a JOIN here instead of fetching the project first and then making a second query to find its organization. A JOIN is much faster and reduces the load on the database connection pool. It gives the controller everything it needs in one trip.

3. Returning a Single Object
Because this is a "Details" page, the controller and the EJS view expect a single project object (project.name, project.description). Returning result.rows[0] directly means the controller doesn't have to extract the first item out of an array. If the ID doesn't exist, rows[0] is undefined, which allows the controller to easily trigger the 404 error page.

Follow-up question:
Why do you think using a parameterized query ($1) is safer than directly inserting a user's input into an SQL query using JavaScript string interpolation?

TRACY:
Using a parameterized query ($1) is safer because it completely prevents SQL Injection (SQLi), which is one of the most common and dangerous vulnerabilities in web applications.

Here is exactly why it happens and why the $1 approach stops it:

1. The Core Problem: Mixing Data and Code

When you use string interpolation (e.g., `SELECT * FROM project WHERE project_id = ${projectId}`), you are combining data (the user's input) with code (your SQL command) into a single string before the database sees it.

If a user inputs a normal number like 1, the query is:
SELECT * FROM project WHERE project_id = 1

But if a malicious user inputs this instead:
1 OR 1=1; DROP TABLE project; --

The database receives this:
SELECT * FROM project WHERE project_id = 1 OR 1=1; DROP TABLE project; --

The database doesn't know the user typed that. It just executes the string exactly as it reads it. It will return all projects (1=1), and then it will delete your entire table (DROP TABLE project).

2. The Solution: Parameterized Queries

When you use a parameterized query, you send the SQL structure to the database first, and the data second.

const query = 'SELECT * FROM project WHERE project_id = $1';
db.query(query, [projectId]);

The database engine parses the query, sees the $1, and knows: "I am expecting a literal value here, not SQL commands."

When you pass the parameter array [projectId], the pg library handles the interaction. Even if the user inputs 1 OR 1=1; DROP TABLE project; --, the database treats that entire string strictly as the project_id. It looks for a project with that exact ID (which won't exist), finds nothing, and returns an empty result.

The Fill-in-the-Blank Analogy

- String Interpolation: Imagine you hand a bank teller a blank piece of paper and a pen, and they write down whatever the customer tells them. If the customer says, "Pay Bob $100, and also empty the vault," the teller writes it down and does it.
- Parameterized Queries: Imagine you hand the teller a pre-printed form that says: "Transfer $[Amount] to [Name]." The teller only allows the customer to write in the blanks. No matter what the customer writes, the teller only treats it as a name and an amount. They cannot add new instructions to the form.

Bonus Benefit: Parameterized queries are also faster. The database can pre-compile the query plan for $1, so if you run it 100 times with different IDs, it reuses the same optimized plan instead of parsing a new string every time.

Follow-up question:
Tracy, why did you use async and await in your controller instead of executing the database functions without waiting for them to finish?

TRACY:
I used async and await because we cannot render the HTML page until we actually have the data from the database.

If I didn't wait for the database functions to finish, the controller would try to send an incomplete page to the user, and the application would crash.

Here is exactly what would happen if you removed await, and why it's necessary:

1. The "Promise" Problem

Without await, the getCategoryDetails() function doesn't return the actual category data. Because database queries take time (even if it's just 10 milliseconds), Node.js immediately returns a Promise (a placeholder object that says, "I'm working on it").

If you didn't use await:

const category = getCategoryDetails(categoryId);
// category is now a Promise { <pending> }, NOT the actual data.

res.render('category', { category: category });
// This crashes! The EJS file tries to read category.name, but category is a pending Promise, not an object.

2. You Can't Render a Page You Don't Have Data For

The entire purpose of this controller is to pass the category object and the projects array to category.ejs. The EJS file has a loop: <% projects.forEach(...) %>.
If we didn't wait for the database to return the projects array, the EJS engine would try to loop over a pending Promise (or undefined), and the site would throw a massive error.

3. It Doesn't Block the Whole Server (The Magic of await)

You might wonder: "If await pauses the function, doesn't that freeze the whole server for everyone else?"

No. This is the beauty of Node.js. await only pauses this specific user's request. While the database is fetching the data for this user, Node.js's event loop is free to handle requests from 10 other users, serve CSS files, and keep the server responsive.

Once the database finishes the query, Node.js picks up exactly where it left off and sends the HTML to the browser.

The Restaurant Analogy

Imagine a waiter (the controller) taking an order to the kitchen (the database).

- Without await: The waiter drops off the order, immediately grabs an empty plate, and serves it to the customer. The customer gets an empty plate because the food wasn't ready yet.
- With await: The waiter drops off the order and waits at the kitchen window. He doesn't leave the restaurant, but he does pause serving that specific table until the chef hands him the finished food. Then he delivers it to the customer.

4. Error Handling

Because we used await, if the database goes offline, the function will fail at that exact line. We can easily wrap it in a try...catch block to catch the error and show the user a 500 error page, rather than letting the whole app crash.

TOPIC 4: ERROR HANDLING

Now we come to our final mandatory topic: Error Handling.

Error handling is important because applications do not always work perfectly.

For example, in your Nonprofit Network application:
- A user might request a project that does not exist.
- A database connection might fail.
- A user might enter an invalid URL.
- A server error might occur while retrieving information.

Your application should handle these situations gracefully instead of displaying confusing technical errors.

There are two important HTTP status codes:
- 404 – Not Found: A user requests a category that does not exist.
- 500 – Internal Server Error: The database connection fails unexpectedly.

Consider this example:

try {
    const category = await getCategoryDetails(categoryId);

    if (!category) {
        return res.status(404).render('404', {
            title: 'Category Not Found'
        });
    }

    res.render('category', {
        title: category.name,
        category
    });

} catch (error) {
    console.error('Error fetching category:', error);

    res.status(500).render('500', {
        title: 'Server Error'
    });
}

Here, try...catch allows the application to catch unexpected errors and display an appropriate error page.

Follow-up question:
Why do you think it is important to have both a 404 error page and a 500 error page instead of using one general error page for every problem?

TRACY:
Having both a 404 and a 500 error page is important because they represent two completely different types of failures. A 404 means the user made a mistake, while a 500 means the server made a mistake.

Here is why separating them is crucial:

1. Clear Communication & User Experience

- 404 (Not Found): This is a client error. The user typed the wrong URL, or clicked an old/broken link. The message should be: "We couldn't find that page. Check the URL or go back home." The user can actually fix this problem themselves.
- 500 (Internal Server Error): This is a server error. The user did everything right, but your database went offline or your code crashed. The message should be: "Something went wrong on our end. Please try again later." Telling a user "Not Found" when the server is actually down is misleading and frustrating.

2. Security

If you use one general error page for everything, you might accidentally expose sensitive information. When a 500 error happens, the raw error message often contains database credentials, SQL syntax, or server file paths (e.g., Error: connect ECONNREFUSED 127.0.0.1:5432).

- A 500 page hides those technical details behind a friendly generic message.
- A 404 page is safe to show because it's just a missing URL, not a system failure.

3. Debugging and Analytics

If you connect your app to a monitoring tool (like Google Analytics or Sentry), status codes tell you exactly where the problem is.

- A spike in 404s means you have broken links on your site that need updating.
- A spike in 500s means your database or server code is currently on fire, and you need to check the logs immediately.

4. Browser and SEO Behavior

Search engines (like Google) treat these codes differently.

- If a search engine crawls a page and gets a 404, it knows to remove that page from its search results.
- If it gets a 500, it knows the server is temporarily broken and will try crawling it again later. If you use a 404 for a server crash, Google might permanently delete your pages from search results by mistake!

Summary
- 404 = "You took a wrong turn." (User's problem, easy to fix).
- 500 = "The bridge collapsed." (Developer's problem, requires technical intervention).
